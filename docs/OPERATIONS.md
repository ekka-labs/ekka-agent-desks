# Running a server

[Back to the start](../README.md)

Everything runs on one machine: EKKA's Enclave, NVIDIA's OpenShell gateway, and Keycloak for sign-in. Every
system of record has a backup and a tested restore. Desk work folders are working state and are not backed up:
your code lives in your repositories.

**Why this page:** a few routine checks keep your agents working and your server safe. Run every command below
from the `deploy/` folder with `sudo`, through `./setup.sh compose ...` rather than a bare `docker compose`: the
setup's own settings are only loaded that way.

## What runs

| Service | Image | Runs as | Data |
|---|---|---|---|
| `keycloak-db` | Postgres 17, by digest | postgres | volume `keycloak-db` |
| `keycloak` | Keycloak 26.7.4, started with `kc.sh start`, by digest | keycloak | in `keycloak-db` |
| `edge` | nginx-unprivileged 1.30.4, by digest | 101 | none |
| `ekka.service` (systemd, not a container) | the signed EKKA release at `/usr/local/bin/ekka`, installed by EKKA's installer | user `ekka` (uid 2000) + group `openshell` | `/var/lib/ekka/.ekka` (vault, desk records, journal) |
| `ekka-desks.service` (systemd) | this compose file, run in the foreground from a root-owned copy, bound to `ekka.service` | root | none |
| `gateway` | NVIDIA's OpenShell 0.1.4, by digest | 1000:1000 + the Docker socket's group + `openshell` | volume `gateway-state`; the Enclave's socket folder `/run/ekka` |
| `gateway-init` | one-shot | root, no network | gives `gateway-state` to uid 1000 |

**Before moving to a new NVIDIA OpenShell version,** run the walk with a person signed in
(`sudo WALK_PERSON_HOME=~/.ekka-walk-person ./up.sh walk`). Its person legs call the gateway directly with
that person's own sign-in: starting a desk, running a command in it, and opening an SSH session into it.
All three must stay refused. A new OpenShell version can change what a method requires.

## The Enclave as a service, and restart recovery

The Enclave is a systemd service, `ekka.service`, generated by EKKA's own `ekka enclave install-service` from the
enrolled home and its owner, with EKKA's shipped hardening (no new privileges, a read-only system, no capabilities, no
setuid). This setup adds one drop-in (`/etc/systemd/system/ekka.service.d/desks.conf`): the `openshell` group for the
interceptor socket, `EKKA_ENV`, and exactly three writable paths: `/var/lib/ekka/.ekka`, `/run/ekka`, `/run/ekka-backend`.
The Enclave reaches the gateway at `https://127.0.0.1:8080` on this machine and checks its certificate against the
public name; it reaches the sign-in service through the edge, by the same name, mapped to this machine in `/etc/hosts`.

The rest of the stack is `ekka-desks.service`: compose in the foreground, from a root-owned copy of `deploy/` and
`tools/` under `/usr/local/lib/ekka-desks` (never a person's checkout), **bound to the Enclave**. Starting the Enclave
starts the stack; stopping or losing the Enclave stops it. Before the gateway starts, the unit connects to the Enclave's
interceptor socket and waits up to a minute for an answer, so a gateway never runs without the Enclave that checks its
calls. A container that exits, cleanly or not, ends the unit, and systemd starts it again (`Restart=always`); compose itself
restarts nothing (`restart: "no"` everywhere). Only `systemctl stop` means stop, and only `systemctl mask` keeps it stopped.
The unit file is `/usr/local/lib/systemd/system/ekka-desks.service` (the folder for units an administrator installs), so
`systemctl mask` can put its `/dev/null` link at `/etc/systemd/system/ekka-desks.service` over it; `up.sh` refuses to run
while that link is there, because a masked stack is a stop somebody meant.

After a reboot or any doubt:

```sh
systemctl status ekka ekka-desks
sudo ./up.sh status
sudo journalctl -u ekka -n 50
sudo journalctl -u ekka-desks -n 50
```

Maintenance: `sudo systemctl stop ekka-desks` stops the stack and leaves the Enclave running until the Enclave is next
started or restarted, which pulls the stack back in; to keep the stack stopped across that and across reboots,
`sudo systemctl mask --now ekka-desks`, and `sudo systemctl unmask ekka-desks && sudo systemctl enable --now ekka-desks` to resume
(measured: `unmask` leaves the unit disabled; the Enclave's drop-in would still pull it in at the next boot, `enable` makes that explicit).
`sudo systemctl stop ekka` stops both. Start with `sudo systemctl start ekka` (the stack follows). An upgrade is the original
`sudo EKKA_VERSION=<release> ./up.sh server <name>` command: it installs the release through EKKA's signed installer,
keeps the previous binary beside it, regenerates the units and restarts them. Rollback is the same command with the older
release and `EKKA_ALLOW_DOWNGRADE=1` added, the one way the installer accepts an older release.

Running the Enclave on this machine's network, as a service, means it is not inside a container: the unit's protections
decide what it can read and reach, and Docker's default seccomp profile does not apply to it. What is gained over the
container: no shared network namespace with the gateway, a start order that fails closed on reboot, the vault on a
host folder only its user and root can read, and the same shape as EKKA's own server install. Root and the Docker socket
remain the trust boundary of this machine.

### Docker Engine maintenance

The units above restart the gateway. They do not recover a desk that
OpenShell has marked as a fatal error. On OpenShell 0.1.4, restarting Docker with live restore
can break the supervisor monitoring connection and leave a desk in `ControlSupervisorExited`.
The normal desk start and stop commands then refuse that desk. This was observed on the test
server; a host reboot did not clear it.

Plan Docker Engine maintenance separately from setup upgrades. Do not treat live restore or this
repair timer as a guarantee that desk work survives an Engine restart. Before maintenance,
finish active work, record each desk's settings (`ekka desk show <desk>`) and keep a
backup of retained data. Do not edit the gateway database or start the desk container directly.

`deploy/harden.sh` restarts Docker only when its Docker settings change (the desk installation checks),
and refuses even then while a desk exists, unless you run it with `ALLOW_DOCKER_RESTART=yes`.
Running it again with unchanged settings does not restart Docker. It also keeps automatic updates from upgrading or
restarting Docker, containerd or runc, so update those by hand, in a planned window.

**If a desk is stuck in this error, you, the server's administrator, recover it** on the installed
machine, through EKKA (measured on the test server):

1. `ekka desk delete <desk>`. Deletion works on a desk in this error, and retires its
   old pin.
2. `ekka desk create <desk> --provider <profile> ...`, with the same settings it had.
   It is registered and pinned as a new desk.
3. Run its setup plan again, as in [Set up your desk](SET-UP-YOUR-DESK.md).

The desk's files are lost: server desks keep their repositories, `.ekka/desk-map.json` and answer
files inside the desk, and deletion removes them. Answers already collected stay on the Enclave.
Approve with `ekka desk repin <desk>` only if `desk show` still lists an old record
for that name.

## What is exposed, and to whom

| Port | Bound to | Who uses it |
|---|---|---|
| 443 | `DESKS_EDGE_BIND` (default `0.0.0.0`) | people's browsers and `ekka`, to sign in. Only the desks realm's paths are forwarded; `/admin`, `/realms/master`, `/metrics`, `/health` and everything else answer 404 |
| 8080 | `DESKS_GATEWAY_BIND` (default `0.0.0.0`) | people's `ekka desk` commands from their own computers, and the desks on this machine (over `127.0.0.1`) |
| 8443 | `127.0.0.1` only | the Keycloak admin console, from this machine |

**On a server, the gateway listens on your network, on purpose:** people use `ekka desk` from their own
computers. Every call is encrypted and needs a person's sign-in. **Allow 8080 and 443 only from your people's
network**: `deploy/harden.sh` does exactly that.

**Before sign-in, the gateway answers one thing to anyone who reaches 8080:** OpenShell 0.1.4's gRPC reflection
lists the API's service and method names. It reveals names only, never data or credentials, but it is one more
reason to keep 8080 on your private network.

**The gateway never trusts client certificates here.** OpenShell 0.1.4 can hand real credential values to an
"operator" (a client certificate with OU=operator under a client CA the gateway trusts). This setup signs everyone
in through OIDC, so the gateway does not start if anything turns that on: a `client_ca_path` or
`[openshell.gateway.mtls_auth]` `operator_enabled`/`enabled` in gateway.toml, `OPENSHELL_TLS_CLIENT_CA`,
`OPENSHELL_ENABLE_OPERATOR_AUTH` or `OPENSHELL_ENABLE_MTLS_AUTH` in its environment, or any command-line flag
(`tools/gateway_preflight.py`, run by `up.sh`, `setup.sh compose up|start|restart|create|run|unpause|scale|watch` and `backup.sh`).
Each reason is named, with its fix. The Enclave also checks the running gateway once a minute and refuses all
desk work (`DESK_GATEWAY_TRUSTS_CLIENT_CERTS`) while it asks for a client certificate, so a gateway started
some other way is caught too. There is no setting to allow either.

Postgres, Keycloak itself and the Enclave control plane are never published. The gateway listener is published
by the gateway container itself; the Enclave is a systemd service on this machine and has no Docker socket.

**The gateway can control Docker on this machine: treat it as root here, and run this setup on a machine used
for nothing else.** A dedicated Docker daemon for the gateway is a further hardening step, not the
supported setup.

### No remote door

This setup serves nothing to a laptop from the Enclave's records: no download of an answer or a receipt, no
remote conversation. Every such read happens on the server, as the administrator: `sudo -i`, then
`ekka run show --output <run>`, `ekka receipts show <run>`, `ekka receipts verify`, or `ekka run attach <run>` for a
running conversation. A laptop's download command against this server is refused by EKKA
(`FETCH_TICKET_ENCLAVE_NOT_REACHABLE`), because the Enclave reports no download address. The edge therefore
carries only the sign-in paths; `/ekka/runs/...` answers 404.

## Start order, and why it matters

`ekka.service` (the Enclave) first. Then `ekka-desks.service`, which waits for the Enclave's interceptor socket to
answer, runs the one-shot folders (`gateway-init`, `backend-init`), then starts `keycloak-db`, `keycloak`, `edge`, the
`gateway` and, once desk administration is on, `ekka-backend`, all in the foreground. The gateway enforces the order
too: **without the Enclave's socket, OpenShell's gateway does not start at all** (measured on 0.1.3). This matters: a
gateway running without EKKA's checks would let the Enclave's machine identity create desks. The order makes that
impossible, and because the stack is bound to the Enclave, a reboot brings it back in this order or not at all.

Check after any restart:

```bash
systemctl is-active ekka ekka-desks
cd deploy && ./setup.sh compose ps
cd .. && sudo ./up.sh status
```

If the stack is down while the Enclave is up, `sudo systemctl start ekka-desks` and read `journalctl -u ekka-desks`.

```bash
./setup.sh compose ps                         # what runs, and its health
./setup.sh compose logs --tail 50 gateway     # one service's log
./setup.sh people                             # the bundle each new person runs once (desks-ca.pem, install.sh)

```

For Enclave maintenance, run the original `sudo ./up.sh server <name>` command from the checkout root.
It reconciles changed configuration and restarts the stack only when something changed, which may interrupt a
conversation. An unchanged, healthy rerun keeps everything running.

## Change a desk

A desk change (`create`, `delete`, `stop`, `start`, `policy set`, `allow`, `deny`, `disconnect`) is an EKKA plan run that only an organization admin may run, and so is `status`, which reads the desk's live state. A plan runs through an Enclave. In this release that means the Enclave on the machine you installed on, so a change runs there, through `up.sh`:

```sh
ekka desk stop code-desk
```

- **Whose sign-in.** It runs under the Enclave's EKKA sign-in, the person who installed the server (an organization admin), whoever types the command. So who may change a desk comes down to who has root on this machine: `sudo -i`, then `ekka desk ...`; the `ekka` command there runs as the Enclave's own user.
- **Not from your own computer.** A person's `ekka` on their own computer reads desks (`list`, `logs`, `policy show`, `connections`). A change from there is refused, because no Enclave runs there. Changing a desk from another computer is not in this release.
- **Reading a desk's policy here needs no sign-in.** On this machine, `ekka desk policy show <desk>` runs the plan `ekka.desk.read.v1` through the Enclave, like `status`, and reads the live policy back from the Enclave's own record of the run. This setup requires EKKA 0.6.12 or newer and installs the general read plan.
- **Policy changes read first.** `allow`, `deny` and `policy set` read the desk's current policy before they change it, so the Enclave needs its own desk sign-in, once: `ekka desk login`. It prints an address. Open it in a browser on a computer set up as in [step 6](SERVER.md#6-each-person-connects-to-the-server), and sign in as `desks-admin`. That sign-in has read permissions only. OpenShell 0.1.4 checks those permissions even for its admin role. The change itself is made by the backend adapter.

## Administer desks from the server itself

**Why:** fewer computers that hold a desks sign-in. An administrator reads desks on the server (over SSH, or AWS Session Manager) instead of setting up their own computer. Desk changes run on the server in any case ([Change a desk](#change-a-desk)).

On the server, once. Point the server's name at the server itself: on a cloud machine its public address is not reachable from inside, because the firewall only lets your VPN in.

```sh
echo "127.0.0.1 desks.internal" | sudo tee -a /etc/hosts      # your server's name
sudo cp -r /var/lib/ekka-agent-desks/people ~/desks-people && sudo chown -R "$USER" ~/desks-people
cd ~/desks-people && ./install.sh desks
```

The sign-in still opens in a browser, so the computer whose browser you use needs the server's name in its hosts file and `desks-ca.pem` trusted, as in [step 6](SERVER.md#6-each-person-connects-to-the-server). Then, on the server:

```sh
ekka desk login             # as desks-admin; one-time password: sudo cat /var/lib/ekka-agent-desks/secrets/first-admin-password
```

Gateway reads such as `ekka desk logs` and `ekka desk connections` now work from the server. With no local desk records, `ekka desk list` also lists the gateway's desks. To see the Enclave's records and pins, use `ekka desk list` and `ekka desk show <desk>`. Changes and live status also go through the Enclave ([Change a desk](#change-a-desk)).

## Updating the desks grant

The CLI uses the organization's `desks` agent; a different `DESKS_AGENT` override is refused.
EKKA 0.6.12 or newer builds and writes the grant through `ekka desk grant update --yes`.
The installer creates the two desk administration plans with `ekka plan create` and writes the
root-owned image, baseline policy, provider ceiling and project records the CLI reads.
It first checks `ekka gate grant list --json` for active `api.read` access on `apis/desks` for this
agent and API gate. Only when missing, it adds a plain read grant with `ekka gate grant add`,
`--capability api.read --ttl 31536000 --no-fingerprint`, without limits. That read access lets the
CLI fetch the adapter's facts even before a write grant exists.

The CLI keeps an unchanged grant, or adds a 365-day grant, reads it back, then removes the old ones.
A refusal or failure stops the installer and preserves the CLI's reason. A failure during removal
may leave the new grant and some old grants in place; inspect `sudo ekka desk grant show --json`
before retrying. If a project update fails, the installer restores the previous project records and
attempts one more grant update. Inspect the CLI answer after a failure; this is not an atomic rollback.

After success, the installer calls `ekka desk grant show --json` and accepts only a `keep` decision
for the expected agent and API gate, with valid FULL limits at `preview.proposed`. It saves those limits atomically in
`/var/lib/ekka-agent-desks/backend/desks-grant.json`, root-owned and mode 0644, for before/after image display and project commands. A failed confirmation stops with the grant
in place and the previous local record retained (unless the disk fails to confirm a completed rename).
The installer never computes a second set of limits.

Before updating, the installer removes the retired window and policy files from the root-owned backend folder.
It unlinks their names without following links and reports removed files in one line. Windows live in the active
grant: the CLI preserves an unexpired window and its original expiry, and drops an expired window on update.
If a grant command reports an outdated server setup, rerun the updated installer before using it.

## Onboarding a project: the discovery window

A project's desk image holds tools only; its dependencies arrive over the network at build time. To learn which hosts
that is, without a guess-and-retry loop, the project's build runs ONCE on a disposable desk in NVIDIA OpenShell's auto
approval mode, and the recommended policy is written from what OpenShell recorded. As root on the server:

```sh
<token> | sudo ekka desk registry login ghcr.io <user>      # once per registry; a read-only token, from a pipe
sudo ekka desk image pull ghcr.io/<org>/<image>@sha256:<64 hex> --signed-by https://github.com/<org>/<repo>/.github/workflows/<build>.yml@refs/heads/main --issuer https://token.actions.githubusercontent.com
sudo ekka desk grant discovery --image ghcr.io/<org>/<image>@sha256:<64 hex> --providers github,bitbucket
sudo ekka desk grant show               # the window: its image, its providers, and when it closes
# the discovery run, through EKKA: it creates discover-<run> from that image, turns auto mode on, builds once,
# reads what OpenShell recorded, turns auto mode off and deletes the desk; then:
sudo ekka desk grant restore
```

The CLI commands are `ekka desk grant discovery --image <ref> --providers <a,b> [--minutes 60] [--yes] [--json]`
and `ekka desk grant restore [--yes] [--json]`. Both preview the change and require the literal word `yes`,
unless `--yes` is supplied. Without a terminal, pass `--yes`. The image must be
`<registry>/<name>@sha256:<64 lowercase hex>`; name 1 to 8 distinct providers already in this server's limits.
Minutes range from 1 to 240, default 60. A second opening is refused while a window is unexpired.
Restore removes even an expired block, keeping project limits; with no block it succeeds without a grant write.

The window does not enforce a one-desk quota. Restore closes the grant window but does not remove already-issued
backend permits, which remain valid until their own expiry unless the desk returns to manual approval mode or is
deleted. Finish the discovery run and clean up its desk as shown above. Simultaneous administrator changes are
not atomic; inspect `ekka desk grant show` after overlapping changes.

What restricts an eligible desk:

- The grant's `discovery` block names the image, the providers and the closing time. The backend adapter turns auto
  mode on only for a desk named `discover-*`, created from that image, holding no other provider, while the window is
  open. Any other desk is refused.
- The adapter writes a permit for that desk only after it reads the setting back as applied, deletes it before it
  turns auto mode off, and deletes it with the desk. The permits live in `/var/lib/ekka-agent-desks/backend/permits`,
  owned by the Enclave's user, 0750, mounted read-write into the adapter's container only.
- The Enclave's gateway interceptor reads that folder (`EKKA_OPENSHELL_DISCOVERY_PERMITS_DIR` in the Enclave's
  `enclave.env`) and lets a desk's policy proposals through only while its permit is present and unexpired. Only the
  adapter's own sign-in (`EKKA_OPENSHELL_BACKEND_SUBJECT`, the `ekka-desk-admin` client) may change the setting. The
  install writes both lines and restarts the Enclave when they change.

OpenShell still holds what it models as risky (private, link-local and metadata addresses, wildcard hosts, database
ports, high ports). Auto mode does not stop code on the desk from sending something it already holds to a public host
it may reach, so the desk gets no production credential.

The image must already be on this machine: OpenShell creates a desk from a local image and pulls with no registry login
(NVIDIA/OpenShell#2676), so `ekka desk image pull` does the pull as root, by digest, with the kept read-only credential
through a Docker login that is deleted right after.

## A project's own desk

The grant holds the image and the policy a desk may be created with. The install puts one of each there: the desk
image it built and the shipped `desk/policy.json`. A project that needs its own tools builds its own image on this
machine, on top of the desk image, and may write its own policy. As root on the server:

```sh
docker image inspect --format '{{.Id}}' <the project image's tag>     # its content ID: sha256:<64 hex>
sudo ekka desk policy check <the project's policy file>               # read back in plain words
sudo ekka desk grant project add <name> --image sha256:<64 hex> --policy <the project's policy file>
sudo ekka desk grant show                                             # both images, both policies, and the project
```

`project add` prints the `ekka desk create` line for the project's desk, with the image's ID and the policy's path.

What keeps a project inside the server's limits:

- **The image is named by its content ID and must already be on this machine.** A tag can be moved to another image;
  an ID cannot. OpenShell never pulls a desk image, so an ID that is not here could never make a desk.
- **The project owns its file and network rules within the server's limits.** File rules must meet the safety floors
  below; the non-root user/group, Landlock setting and policy version stay exactly as shipped.
  Network rules may open no host outside the ceiling (the hosts this server's provider profiles name).
  A project that needs a new host adds a provider profile, which is how a host reaches a desk.
- **The backend adapter decides at create.** The grant lists the allowed images and policies by digest; a create with
  any other image or policy is refused (`CONSTRAINT_IMAGE_DIGESTS`, `CONSTRAINT_POLICY_DIGESTS`). The copy of the
  policy the Enclave reads sits in its own home; a changed copy has another digest and is refused.
- **Nothing else in the grant changes.** The shipped image and policy stay, and a project opens no auto approval.

The records are root-owned files in `/var/lib/ekka-agent-desks/backend/projects/`, read by the CLI on every grant
update, so `sudo ./up.sh server <name>` and an upgrade keep a project. After a rebuild the image has a new ID: run
`project add` again with it, and the old ID leaves the grant. `sudo ekka desk grant project remove <name>` takes the
project out; its desks are not deleted, and no new one can be created from it.

### Project file safety floors

Start with `desk/policy.json`. For example, project `acme` can add `/opt/project-tools` to `filesystem.readOnly` and
`/var/cache/acme` to `filesystem.readWrite`, then run `project add` with that file. Create the folders in its image
and give the shipped user permission to use them; a policy grants access, it does not create folders or change ownership.

- `filesystem` holds only `includeWorkdir`, `readOnly` and `readWrite`. Keep `includeWorkdir` exactly as shipped;
  the two path lists contain strings, without duplicates or a path appearing in both lists. Unknown policy keys
  are refused too. The process user/group and `landlock` objects, including their keys, must match the shipped ones.
- Paths are absolute and already normalized: no `.` or `..` components, repeated slashes, trailing slash (except
  `/` itself), glob characters (`* ? [ ] { }` or backslash), or control/invalid Unicode characters. The limit is
  4095 UTF-8 bytes. Root passes the spelling check but is refused as a protected location.
- Keep every shipped read-only entry. Additional reads may be under an already shipped readable or writable path,
  `/opt/project-tools`, `/opt/projects/<name>`, `/var/cache/<name>`, `/sandbox/ekka-workspace` or
  `/sandbox/.ekka-inputs`. Device and process paths are exceptions: keep the exact shipped entries, but add no
  rules below `/dev` or `/proc`, where links such as `/proc/self/root` could resolve outside the named tree.
- Writes may keep or remove shipped entries and add paths under `/tmp`, `/opt/projects/<name>` or
  `/var/cache/<name>`. Here `<name>` is the exact project name passed to `project add`; a neighboring name does not
  match. This permits project caches and tools without opening all of `/opt` or `/var/cache`.
- No new write may equal, contain or sit below `/bin`, `/sbin`, `/usr`, `/lib`, `/lib32`, `/lib64`, `/libexec`,
  `/etc`, `/proc`, `/sys`, `/dev`, `/boot`, `/root`, `/run`, `/var/run`, `/var/lib`, `/var/log`, `/home`,
  `/.openshell`, `/sandbox/ekka-workspace` or `/sandbox/.ekka-inputs`. Thus `/var` and `/sandbox` are refused too.
  The workspace already gets write access through `includeWorkdir`; staged inputs must not get a new write grant.
  Only the exact shipped `/dev/shm` and `/dev/null` write entries are allowed under `/dev`, with no extra descendants.
- New reads also refuse ancestors and descendants of `/root`, `/home`, `/run`, `/var/run`, `/var/lib`, `/proc`,
  `/sys`, `/dev`, `/boot` and `/.openshell`, except the exact shipped read-only entries.
  All home directories are excluded because the policy cannot prove their ownership. Unrecognized locations such
  as `/host`, `/mnt` and `/data` are refused for both reads and writes, rather than guessing whether they hold secrets.

These are checks of path spelling inside the desk, not checks of the custom image's symlinks or mounted contents.
The administrator must ensure allowed folders resolve to the intended project data and contain no host or other
tenant's secrets. A read-only rule grants reads; it cannot cancel writes granted by a parent or `includeWorkdir`.
In particular, these checks do not prove staged inputs are read-only if the actual working directory covers them.
The gateway disables host bind mounts and caller-supplied driver configuration; file rules do not enable either.

The shipped `desk/policy.json`, including `/dev/shm`, stays unchanged. Existing desks are pinned to its current
baseline digest; changing that entry requires a separate migration. These floors admit a new project's creation
policy, not a live change to an existing desk's pinned filesystem baseline.

## The backend adapter's image

The backend adapter, which carries desk administration through EKKA, runs from EKKA's public image `ghcr.io/ekka-labs/ekka-backend`, built from the public repository `ekka-labs/ekka-backend` and pinned by digest in `deploy/pins.json`. No registry login is needed, and none is kept on this machine.

`up.sh` pulls the pinned digest and checks its signature with cosign before anything runs it. The signature must come from the release workflow of `ekka-labs/ekka-backend` on a version tag; any other image does not run.

## Connect a provider's key

A provider's key is set on this machine, at install or when it changes. People's own `ekka desk connect` points here. The key comes from a pipe, never as an argument and never typed at the terminal, so it is not on screen, in `ps` or in shell history:

```sh
gh auth token | sudo ekka desk connect github
sudo cat /root/anthropic.key | sudo ekka desk connect claude-code
```

It creates the provider with that key, or replaces the key of one that exists, then updates the desks grant to name that provider, through `ekka desk grant update --yes`, the same command the install uses (the new grant is read back before the old ones are revoked). The key is handed only to NVIDIA's CLI, in the variable the provider's profile names (`GITHUB_TOKEN`, `ANTHROPIC_API_KEY`). The call is logged like the commands below, with the key's name, never its value. A provider that needs more than one key, such as `codex`, is refused here.

## NVIDIA's own commands, as the gateway's administrator

**Why:** providers and their keys are set at install, on this machine, and some need the gateway's administrator, for example a provider whose keys the gateway mints itself (AWS through STS). `up.sh` runs NVIDIA's pinned `openshell` CLI as that administrator for the length of one command, then switches that identity off again.

It runs only these commands, and refuses every other one by name with "desk changes run through EKKA: ekka desk <op>":

| Kind | Commands |
|---|---|
| Reads | `status`, `sandbox list`, `sandbox get`, `provider list`, `provider get`, `provider list-profiles`, `provider refresh status` |
| The kill switch | `sandbox stop <desk>`, always with the desk's name ([When EKKA's cloud is unreachable](#when-ekkas-cloud-is-unreachable)) |
| Provider setup | `provider create`, `provider update`, `provider delete`, `provider refresh configure`, `provider refresh rotate`, `provider refresh delete` |
| A file copy | `sandbox upload <desk> <local path> [/sandbox/<folder>/]`, `sandbox download <desk> /sandbox/<path> <empty folder>` ([below](#copy-files-into-and-out-of-a-desk)) |

A secret is never an argument: name the key and pass its value in the environment (`--credential KEY`, `--secret-material-env`). `--credential KEY=VALUE`, `--secret-material-key` and `--from-oidc-token` are refused. Each allowed call is logged before it runs, with the command and the person who ran sudo, in `/var/lib/ekka-agent-desks/openshell-admin.log` (mode 0600).

```sh
sudo ./up.sh openshell provider list
```

Secret material goes through the environment, never an argument, as NVIDIA's `--secret-material-env` expects:

```sh
sudo --preserve-env=SOURCE_SECRET ./up.sh openshell provider refresh configure aws --credential-key AWS_ACCESS_KEY_ID --strategy aws-sts-assume-role --material role_arn=<role> --secret-material-env aws_secret_access_key=SOURCE_SECRET
```

## Copy files into and out of a desk

EKKA has no governed copy yet, so the server's administrator copies with NVIDIA OpenShell's own commands, through the
same door as above. Use it for what a repository cannot carry: a design document in, a `git bundle` of the work out.

```sh
sudo ./up.sh openshell sandbox upload code-desk /srv/in/design.md /sandbox/ekka-workspace/reference/
sudo install -d -m 0700 /srv/out/2026-11-14
sudo ./up.sh openshell sandbox download code-desk /sandbox/ekka-workspace/out/work.bundle /srv/out/2026-11-14
```

What keeps it safe:

- **The desk is named, and both paths on the desk are under `/sandbox`.** OpenShell checks the desk's side again and
  refuses a path that leaves the desk's work folder, also through a link.
- **A download is the direction to be careful with.** It runs as root, and the archive was made by a `tar` inside the
  desk, so the desk decides every byte. It lands only in a folder that exists, is empty, belongs to the administrator
  and that nobody else can write. Right after, every link and special file is removed and every setuid, setgid and
  write-by-others bit is cleared, whatever the copy's result, so root never reads through a link a desk made. The
  command prints what it removed.
- **Prefer one file to a folder.** A `git bundle` is one file, and `git bundle verify` plus the commit IDs say what it
  holds.
- **Each call is logged** with the command and the person who ran sudo. It is outside EKKA's record: no receipt.

An upload sends what the administrator names. Check that it holds no key and no `.env` before it goes in: a desk's
agent reads everything in its work folder, and what it reads can reach the AI provider.

## Certificates

`certs.sh` made a local CA (5 years) and the server certificates (1 year). Check them monthly:

```bash
sudo ./certs.sh check                              # exit 1 when anything expires within 30 days
sudo ./certs.sh renew <server name> && sudo ./setup.sh compose restart edge gateway
```

People's computers trust the desks CA: the browser through the operating system, and `ekka` through
`backend.json`'s `ca_pem_path`, which `install.sh` writes. With a certificate from a public CA, nothing is installed on people's computers.

The browser half, once per computer, with `desks-ca.pem` from the people bundle:

| System | Trust it, as the person, no sudo | Take the trust away |
|---|---|---|
| macOS | `security add-trusted-cert -r trustRoot -p ssl -s <server name> -k ~/Library/Keychains/login.keychain-db desks-ca.pem` | `security remove-trusted-cert desks-ca.pem` |
| Linux, Chrome and Chromium | `certutil -d sql:$HOME/.pki/nssdb -A -t C,, -n "EKKA desks CA (<server name>)" -i desks-ca.pem` (`certutil` is in `libnss3-tools`) | `certutil -d sql:$HOME/.pki/nssdb -D -n "EKKA desks CA (<server name>)"` |

`install.sh` prints the right one for the computer it runs on, with the CA's SHA-256 fingerprint, and runs
nothing; `./trust-ca.sh --all` in the bundle prints both. Read people the fingerprint `ekka desk invite` shows, so they
can check the CA they received before their browser trusts it.

The trust is as narrow as each system allows: websites only, the server's name only, that person only. The CA's own
constraint names DNS names and IP addresses alone, so a CA trusted for every purpose (the old
`sudo security add-trusted-cert -d ... System.keychain`) would also let anyone holding the server's CA key sign
software or mail that computer trusts. On Linux, Chrome and Firefox do not read the system store, so
`update-ca-certificates` needed root for the whole machine and still left the warning.

A restricted Windows trust procedure is not provided yet; meanwhile, use the documented setup on a macOS or Linux computer.

Firefox keeps its own store: import `desks-ca.pem` under Settings, Certificates, Authorities, or turn on
`security.enterprise_roots.enabled`.

## Rotating credentials

| What | How |
|---|---|
| The Enclave's client secret | regenerate it in the Keycloak admin console (client `ekka-enclave`, Credentials), then `./setup.sh enclave-secret <env>`. The Enclave reads it from its vault each time it makes a token: no restart |
| People's sessions | Keycloak admin console, the person's Sessions, sign out. They sign in again at their next command |
| A company key (Anthropic, GitHub, ...) | on the server, `<new key> \| sudo ekka desk connect <profile>` ([above](#connect-a-providers-key)). It replaces the key for every desk at once |
| The gateway's signing key | it is pinned in the Enclave (`EKKA_OPENSHELL_GATEWAY_KEY_B64`, derived from `tls/jwt/public.pem`). Replace the key, run `./setup.sh enclave-config <env> <workspace>`, then run the original `sudo ./up.sh server <name>` command from the checkout root for full-stack maintenance. Every call is refused until both match |

## Upgrades

Upgrade this setup and the Enclave together, in one maintenance window. The installer refuses to install on an older Enclave than its minimum supported release. Take a backup first; upgrades can interrupt running jobs and conversations.

1. Record the current repository commit and configured EKKA version so you can return to them.
2. Run `git pull` in this repository on the server.
3. Rerun the original installation command, such as `sudo ./up.sh server <name>`. Replace `<name>` with the installed server name.
4. Check `sudo ./up.sh status`, then run `sudo ./up.sh walk` and a sample question before resuming work.

The installer installs the pinned EKKA release through EKKA's signed installer (the previous binary is kept beside it), regenerates the Enclave's unit with `ekka enclave install-service`, refreshes the root-owned copy the stack runs from, initializes the pinned base-image submodule, builds the desk image locally, and restarts the units only when something changed. Existing desks keep their previous image until recreated. Save any work you need before deleting a desk.

Update one component at a time:

- **EKKA Enclave:** use the release this setup configures. An explicit override, such as `sudo EKKA_VERSION=0.6.12 ./up.sh server <name>`, must be compatible with the integration's minimum release.
- **Base image:** change `desk/image/` in a reviewed pull request; the next install or upgrade builds it. There is one Dockerfile, here.
- **OpenShell:** update the release and image pins together. Verify checksums and run the integration checks before installing the change.
- **Keycloak and Postgres:** back up their data before changing image pins. Startup may migrate the database; restoring an older image alone may not reverse a migration.

For rollback, restore the previous integration commit and compatible EKKA version, then rerun the installation command. If a database migration ran, follow the component's recovery instructions and restore its backup where required.

Receipts and exports may include a requester's name or email when supplied at dispatch. Treat these records according to your retention policy. Those identity fields grant no authority.

## When EKKA's cloud is unreachable

Every desk change normally goes through EKKA: `ekka desk stop`, `ekka desk start` and the rest. If EKKA's cloud cannot be reached and a desk must stop now, stop it on the server. Nothing below needs EKKA.

**One desk.** The sign-in service and the gateway on the server must be running.

```sh
sudo ./up.sh openshell sandbox stop <desk>    # always name the desk: with no name it stops the last one used
```

The desk stays stopped until someone starts it again.

**Every desk at once.** Stop the stack's unit and keep it stopped. The gateway stops each running desk before it exits; the
stack (sign-in included) stays down, even after a reboot or an Enclave restart, until you unmask it. Stopping the gateway
container by hand does not work here: the unit would start the stack again.

```sh
sudo systemctl mask --now ekka-desks                                  # up to 90 s: the gateway stops every desk first
sudo docker ps --filter label=openshell.ai/managed-by=openshell       # should list nothing
```

If the second command still lists containers, the gateway ran out of time. Stop them directly:

```sh
sudo docker stop $(sudo docker ps -q --filter label=openshell.ai/managed-by=openshell)
```

To stop only one desk's containers this way, add `--filter label=openshell.ai/sandbox-name=<desk>`.

When EKKA is back: `sudo systemctl unmask ekka-desks && sudo systemctl enable --now ekka-desks`. The gateway starts again every desk that was running when you stopped it. A desk you stopped with `sandbox stop` stays stopped.

## Remove the server's desks

This deletes your desks, the keys you connected, the sign-in accounts and the Enclave's vault. Back up first if you might want them ([Backup and restore](#backup-and-restore)).

```sh
sudo -i
ekka enclave list                                   # note this machine's Enclave id
ekka enclave revoke <id>                            # removes it from your EKKA organization; do this FIRST
systemctl disable --now ekka-desks ekka             # the stack, then the Enclave
docker rm -f $(docker ps -aq --filter label=openshell.ai/managed-by=openshell)          # each desk's container
docker volume rm $(docker volume ls -q --filter label=openshell.ai/managed-by=openshell)   # each desk's volumes
cd /usr/local/lib/ekka-desks/deploy && ./setup.sh compose down -v   # the stack's containers and volumes
rm -rf /var/lib/ekka-agent-desks /var/lib/ekka/.ekka
```

The order matters. `ekka enclave revoke` needs the sign-in that the last line deletes, so it runs first. The desks'
own containers and volumes do not belong to the stack, so `compose down -v` leaves them: remove them by their label.
If the server has no desk, the two `docker` lines print a usage error and change nothing.

## Backup and restore

```bash
./backup.sh backup [<dir>]       # one dated folder, mode 0700: Keycloak's dump, the gateway's volume, the Enclave's home, $DESKS_STATE
./backup.sh restore <folder>     # refuses unless every file matches the folder's SHA256SUMS
```

The stack and the Enclave are stopped while their state is copied (a minute), and started again only if the Enclave
was running before.

**Restoring onto a server that was set up again after the backup** (a rebuilt machine is the usual reason to restore).
The restore puts back the desks' certificate authority and the copy the Enclave trusts, so the Enclave can reach the
sign-in service again. Two things live outside any backup, and the restore names them when it sees a different
Enclave than the one it replaced:

1. The organization's desk plans still point at the Enclave the new setup created. Run the install line once more,
   `sudo ./up.sh server <name>`; it points them at the restored Enclave.
2. Desk work folders are not in a backup. Make each desk again, `ekka desk create <desk> --provider <profile>`, and
   revoke the Enclave the restore replaced, `ekka enclave revoke <id>`. **A backup is a secret:** it holds the Enclave's vault and the key that unlocks it. Keep it where you keep
passwords.

Discovery windows live in the active grant and are not restored from a local backup. Backups exclude the retired
window and policy files; restore excludes them from older archives and safely unlinks any already on the machine
before restarting services. Check `ekka desk grant show` after restoring.

Tested: back up, destroy every volume and a certificate, restore. The sign-in realm, the administrator, both
volumes with their owners and modes, and the certificate came back. A tampered backup is refused before anything
is touched.

## A desk change that never finished

A desk change (start, stop, create, delete and the others) can reach the backend adapter's deadline before it is done. The plan's step then fails, and the change is named by its request id, a lowercase UUID such as `3f1c2a9e-5b7d-4e2a-9c1b-7d6e5f4a3b2c`. `ekka desk status <desk>` prints it, and the desk stays locked to it (`admin:3f1c2a9e-...`), so no job and no other change can use the desk meanwhile.

Usually the next `ekka desk status <desk>` settles it on its own. When status says the change cannot be settled from what the backend reports, settle it on the machine:

```sh
sudo ./up.sh desks settle code-desk --operation 3f1c2a9e-5b7d-4e2a-9c1b-7d6e5f4a3b2c
```

It checks that the desk's lock names exactly this change and does nothing otherwise. Then it restarts the gateway. **That restart stops every running desk on this machine, not only this one, and interrupts their jobs**: NVIDIA's gateway stops the desks it manages when it shuts down. Then it watches the desk's containers until none is starting, restarting or being removed and nothing has changed for 40 seconds (NVIDIA OpenShell's 10-second stop timeout plus 30). Only then does it write one settle marker for this change, `settle/<request id>.json`, into the adapter's state. It gives up after 10 minutes and writes nothing. For a deleted desk, whose containers are gone, add `--backend-id <id>` from `ekka desk status`. For a create that never reached the desk, no container carries its labels: the procedure writes the marker with no backend id and no containers, and the adapter accepts that only for a create it cannot find either. It then answers `NOT_APPLIED`: nothing was created.

**The hold.** Before it restarts the gateway, the procedure writes a hold for the change, `settle/<request id>.hold` in the adapter's state. While the hold exists, the adapter never re-issues that change, so a `status` during the quiet window cannot send it again after the restart. The procedure removes the hold when it writes the marker. If the procedure stops without a marker (the desk kept changing, the gateway did not restart, or it was interrupted), the hold stays, and the message says so. Check the desk with `ekka desk status <desk>`, then remove the hold:

```sh
sudo ./up.sh desks unhold <desk> --operation <request id>
```

Unhold removes the hold only while that desk's lock still names the change, or when the settle that wrote the hold recorded this desk for it and the desk's lock no longer names the change (the change ended meanwhile). The hold itself names no desk, so a request id from another desk is refused and nothing is removed. One settle or unhold runs at a time on the machine. After that the adapter may re-issue the change, or you settle it again.

Then run `ekka desk status code-desk` again. The adapter reads the marker once, settles the change and frees the desk.

## When something fails

| Symptom | Cause | What to do |
|---|---|---|
| `ekka-desks` failing, log says "wait-interceptor: nothing answers" or the gateway says "gateway interceptor initialization failed" | the Enclave is down or not enrolled | `sudo journalctl -u ekka`; the stack starts once the Enclave answers on its socket |
| `gateway` restarting, "unable to open database file" | `gateway-state` is not uid 1000's | `./setup.sh compose up gateway-init` |
| people's commands say the issuer's certificate is not trusted | an old `ekka`, or `install.sh` not run | upgrade `ekka`; run `install.sh` |
| every Enclave call refused after a gateway key change | the pinned key is stale | `./setup.sh enclave-config <env> <workspace>`, restart the Enclave |
| Keycloak down | runs refuse by name (`OPENSHELL_EXECUTOR_ISSUER_UNREACHABLE`), no gateway call is made | start Keycloak; the next run makes a token |
| a plan run is refused: no grant | the desks agent has no grant for that desk | `ekka gate grant list`; the install made one for `desks/*` |
| `ekka desk create` refused: a key is missing | the desk names a key nobody connected yet | `ekka desk connections`; connect it first, then make the desk |
| the browser warns about the sign-in page's certificate | this computer does not trust the server's certificate authority yet | trust `desks-ca.pem` from the people bundle ([Certificates](#certificates)) |

### A long wait reports an expired EKKA session

A run can finish even when `plan run` reports `session expired` while waiting. Read the existing run rather than dispatching it again:

```sh
ekka run list --limit 10 --json
ekka run show <full-run-id>
```

Choose the full `id` belonging to your plan and start time in the JSON list. `run show` reads that run's result; it does not start another run. On the Enclave's machine it also shows the collected answer, labelled as the local copy. Refreshing the session during a long wait is a runner follow-up; this recovery path is available now.

## Known differences from NVIDIA's documentation (OpenShell 0.1.3)

- The supervisor binary in `ghcr.io/nvidia/openshell/supervisor:0.1.3` is `/openshell-supervisor`, not the
  `/openshell-sandbox` the container-deployment page names.
- `openshell-gateway generate-certs` has no lifetime option and issues certificates valid until the year
  4096. This setup makes its own (`certs.sh`).
- `openshell gateway add https://...` without `--local` is taken for a cloud gateway and waits two minutes
  for a browser sign-in.
- The gateway image runs as uid 1000 but owns no folder for it, so a fresh state volume cannot hold its
  database. NVIDIA's own compose runs the gateway as root; this setup uses `gateway-init` instead.
- Desk supervisors use the host network and reach the gateway on `127.0.0.1`, so the host port must equal
  the gateway's own port.
- Neither the gateway nor the supervisor image carries a signature or attestation. This setup pins both
  by digest, and checks each binary against NVIDIA's checksummed release (`tools/verify_pins.py`).
